# Verbalized Sampling 기반 IP 아이디어 생성기 마스터 제작문서

## 1. 프로젝트 정의

### 1.1 제품명

가칭: **IP Diversity Engine**

### 1.2 해결하려는 문제

일반적인 LLM 아이디어 생성은 한 번에 하나를 요청하거나 “10개를 나열하라”고 요청한다. 이 방식은 다음 문제를 만든다.

- 동일 장르·산업에서 비슷한 클리셰가 반복된다.
- 여러 번 호출해도 첫 호출의 인기 패턴과 유사한 결과가 재생산된다.
- 후보 수는 많아져도 의미적 범위는 넓어지지 않는다.
- 낮은 확률의 유효한 해결책보다 익숙하고 말하기 쉬운 해결책이 우선된다.
- 생성 결과의 참신함, 품질, 구현 가능성, 선행기술 충돌을 한 점수로 섞어 평가한다.

### 1.3 제품 목표

사용자의 문제·도메인·제약을 입력받아 다음 산출물을 만든다.

1. 대중적 기준안 1~2개
2. 의미적으로 다른 중간 후보 2~4개
3. 저전형성 꼬리 후보 3~10개
4. 중복 제거된 우선 검토 포트폴리오
5. 각 후보의 기술 구성, 기술적 효과, 구현 경로, 위험, 선행기술 검색 키워드
6. 특허·연구·제품 기획으로 넘길 수 있는 구조화 문서

## 2. 논문에서 가져오는 핵심 메커니즘

### 2.1 문제 모델

선호학습은 익숙하고 유창하며 예측 가능한 답을 선호하는 전형성 편향을 포함할 수 있다. 여러 답이 모두 쓸 만한 창의 과제에서는 이 편향이 동률 결정자처럼 작동해 일부 상투적 응답으로 확률 질량을 집중시킨다.

### 2.2 VS의 핵심

직접 프롬프트:

> 이 문제를 해결할 아이디어 하나를 제안하라.

목록 프롬프트:

> 아이디어 다섯 개를 제안하라.

분포 프롬프트:

> 서로 다른 아이디어 다섯 개와, 각 아이디어가 전체 가능한 응답 분포에서 나타날 것으로 모델이 추정하는 전형성 값을 함께 제안하라.

후보의 텍스트와 전형성 추정치를 함께 생성하면, 단일 정답 모드가 아니라 “대표적인 분포” 자체가 출력 목표가 된다.

### 2.3 제품화 시 반드시 수정할 부분

논문은 `probability`라는 표현을 사용하지만, 제품 UI와 IP 문서에서는 다음 용어를 쓴다.

- 내부 필드: `typicality_estimate`
- 사용자 표시: `모델 추정 전형성`
- 설명: `전체 가능한 응답 분포에서 이 후보가 얼마나 흔할 것으로 모델이 추정하는지 나타내는 휴리스틱 값`

이 값은 다음이 아니다.

- 실제 시장 성공 확률
- 실제 특허 등록 확률
- 통계적으로 교정된 발생 확률
- 선행기술 존재 확률
- 품질 점수

## 3. 관련 연구를 반영한 확장 설계

### 3.1 진단 연구에서 반영할 것

- 정렬 모델이 기초 모델보다 창의·무작위 과제에서 더 예측 가능해질 수 있다.
- 공동 집필에서도 정렬 모델의 제안이 사용자 결과를 서로 비슷하게 만들 수 있다.
- 생성 텍스트의 표면적 차이보다 플롯·개념 단위의 중복을 측정해야 한다.

따라서 단순 문자열 중복 제거가 아니라 임베딩 기반 의미 중복 제거가 필요하다.

### 3.2 추론 시점 연구에서 반영할 것

- VS: 후보와 전형성 추정치를 함께 생성한다.
- SimpleStrat: 먼저 의미 축을 나누고 각 층에서 생성한다.
- Growing a Tail: 온도, 관점 다양화, 모델 조합을 함께 쓸 수 있다.
- Dynamic Context Evolution: 여러 배치에 걸친 의미 메모리와 프롬프트 회전을 적용한다.

결론적으로 본 제품의 생성기는 **Stratified VS + Semantic Memory** 구조로 설계한다.

### 3.3 교정 연구에서 반영할 것

모델이 말한 수치는 프롬프트·모델·과제에 따라 교정 정도가 달라진다. 따라서 숫자의 절대값을 사실로 취급하지 않고 다음 방식으로만 사용한다.

- 후보 내 대략적 전형성 순위
- Head/Mid/Tail 밴드 분류
- 임계값 기반 탐색 제어
- 반복 실험에서 상대 변화 비교

## 4. 사용자 워크플로

### 4.1 입력

- 도메인
- 해결할 문제
- 대상 사용자 또는 수요처
- 현재 방식과 불편
- 필수 제약
- 제외할 방식
- 사용 가능한 기술·센서·데이터·장비
- 사업 또는 연구 목표
- 특허화를 원할 경우 공개된 선행 아이디어 요약

### 4.2 생성 파이프라인

1. **Brief Normalizer**: 입력을 문제-원인-제약-효과 구조로 정규화한다.
2. **Baseline Mapper**: 가장 전형적인 해결책과 클리셰를 3개 이내로 명시한다.
3. **Strata Builder**: 해결 공간을 4~8개 의미 축으로 분할한다.
4. **VS Generator**: 층별 후보를 `k=5`씩 생성한다.
5. **Constraint Validator**: 금지조건·기술조건·형식을 검사한다.
6. **Semantic Memory**: 기존 결과와 의미 유사도를 계산하고 중복을 제거한다.
7. **Quality Gate**: 효용·구현성·명확성·위험을 평가한다.
8. **Novelty Challenger**: “왜 실제로 새롭지 않을 수 있는가”를 반대 관점에서 검토한다.
9. **Portfolio Selector**: Head/Mid/Tail이 섞인 포트폴리오를 고른다.
10. **IP Handoff**: 검색식, 핵심 구성, 기술적 효과, 청구항 씨앗을 문서화한다.

### 4.3 출력

최종 후보마다 다음을 제공한다.

- 아이디어명
- 한 줄 정의
- 해결 문제
- 핵심 메커니즘
- 기존 방식과의 구조적 차이
- 기대 기술적 효과
- 최소 구현 예
- 모델 추정 전형성
- 의미 층/탐색 축
- 품질 점수
- 위험·반례
- 선행기술 충돌 예상
- 검색 키워드
- 독립항 씨앗
- 종속항 변형 방향
- 검증 실험

## 5. 생성 모드

### 5.1 Standard

전체 분포에서 후보 5개를 생성한다. 초기에 주제 공간을 파악할 때 사용한다.

### 5.2 Balanced Portfolio

- Head 1개: 0.20 이상을 목표
- Mid 2개: 0.08~0.20을 목표
- Tail 2개: 0.08 미만을 목표

수치는 절대 규칙이 아니라 프롬프트 제어용 기본값이다.

### 5.3 Tail Exploration

모든 후보의 `typicality_estimate`가 임계값 `tau` 미만이 되도록 요청한다. 기본 `tau=0.10`; 지나치게 빈 출력 또는 품질 저하가 발생하면 0.15→0.20 순으로 완화한다.

### 5.4 Stratified

모델이 먼저 다음과 같은 탐색 축을 만든 뒤, 각 축에서 최소 1개를 생성한다.

- 물리적 구조
- 센서·데이터
- 제어 알고리즘
- 인간-기계 상호작용
- 운영 프로세스
- 비즈니스 모델
- 안전·규제
- 유지보수·모듈화

### 5.5 Multi-Batch

한 호출에 지나치게 많은 후보를 요구하지 않는다. `k=5`를 기본으로 여러 배치를 실행하되, 매 배치에 기존 후보의 임베딩 요약·금지 개념·미탐색 층을 넣는다.

## 6. 선택 정책

### 6.1 아이디어 탐색 화면

한 후보를 자동 선택하지 않고 전체 포트폴리오를 보여준다.

### 6.2 현실적 사용자 시뮬레이션

반환 후보의 전형성 값을 후보 집합 안에서 재정규화하여 추첨할 수 있다. 이때 표시 문구는 `후보 집합 내 재표본화`로 한다. 실제 전체 분포 표본이라고 주장하지 않는다.

### 6.3 혁신 후보 자동 선정

품질 게이트를 통과한 후보에 한해 다음 요소를 조합한다.

- 낮은 전형성 순위
- 낮은 기존 후보 유사도
- 높은 기술적 효과
- 높은 구현 가능성
- 낮은 선행기술 충돌 예상

전형성 값 하나만으로 고르지 않는다.

## 7. 품질 평가

### 7.1 생성 품질 지표

- `semantic_diversity = 1 - mean_pairwise_cosine_similarity`
- 중복률: 최대 유사도 0.88 이상 후보 비율
- 제약 통과율
- JSON 파싱 성공률
- 층별 커버리지
- 품질 루브릭 평균
- 인간 평가 일치도

### 7.2 IP 품질 루브릭

제안 가중치:

- 기술적 차별성 25
- 기술적 효과의 명확성 20
- 구현 가능성 20
- 회피설계·권리화 가능성 20
- 수요 적합성 15

이 점수는 내부 선별 점수이며 법적 특허성 판단이 아니다.

### 7.3 MVP 승인 기준

제안 기준:

- Direct 대비 의미 다양성 +25% 이상
- 품질 점수 하락 5% 이내
- 제약 통과율 90% 이상
- JSON 유효성 99% 이상
- 의미 중복률 10% 이하
- Head/Mid/Tail 중 최소 2개 밴드 포함률 95% 이상

## 8. 기존 앱 통합 우선순위

### P0 - 의미 오류 수정

1. 세계관 후보 5개의 확률 합계를 100%로 강제하는 규칙 제거
2. `확률` 표시를 `모델 추정 전형성`으로 변경
3. 숨겨진 3개 후보를 내부적으로 생각하라는 제목 프롬프트를 실제 구조화 후보 출력으로 변경
4. 단계별 사고과정 공개 요구를 짧은 검토 근거로 변경
5. JSON Schema 검증과 자동 복구 추가

### P1 - 생성 엔진 개선

1. Standard/Balanced/Tail/Stratified 모드
2. 후보 카드의 Head/Mid/Tail 배지
3. 배치 간 임베딩 중복 제거
4. 품질 게이트와 재생성
5. 후보 비교·핀·병합 기능

### P2 - IP 문서화

1. 기술구성 분해
2. 선행기술 검색식 생성
3. 독립항 씨앗과 종속항 변형
4. 검증 실험과 증거 계획
5. Markdown/JSON/ZIP 내보내기

## 9. 보안·운영

- 공개 배포 시 API 키는 서버 환경변수 또는 비밀관리 서비스에 저장한다.
- 클라이언트에는 단기 세션 토큰만 제공한다.
- 요청·응답 스키마를 서버에서 검증한다.
- 프롬프트와 모델 버전을 결과 메타데이터에 기록한다.
- 동일 브리프에 대한 seed, temperature, tau, k를 로그로 남긴다.
- 사용자 비공개 발명 정보는 학습·분석 로그에서 제외할 수 있도록 설정한다.

## 10. 완료 정의

제품은 단순히 후보를 많이 생성했다고 완료되지 않는다. 다음이 모두 충족되어야 한다.

- 결과가 의미적으로 분산되어 있다.
- 각 후보가 입력 제약을 지킨다.
- 수치가 실제 확률이나 특허성으로 오해되지 않는다.
- 이전 후보와의 중복이 관리된다.
- 저전형성 후보가 품질 게이트를 통과한다.
- 최종 산출물이 조사·기획·출원 준비 문서로 연결된다.
